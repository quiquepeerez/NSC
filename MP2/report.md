# Mandelbrot Set – Performance Scaling Report

---

## 1. The Problem

The goal of this miniproject is to compute the Mandelbrot set and analyze the performance of multi-processing and distributed implementations.


For each complex number

$$
c = x + iy
$$

we compute the iterative sequence:
$$
z_(n+1) = z_n² + c
z_0 = 0
$$


A point belongs to the Mandelbrot set if the magnitude of `z` remains bounded.  
In practice we use an escape condition:
$$
|z| > 2
$$


If this condition occurs, the point is considered to have escaped. Otherwise, if the sequence does not escape after a fixed number of iterations (`max_iter`), the point is assumed to belong to the set.

The Mandelbrot image is generated by evaluating this iterative process for every pixel in a grid covering a region of the complex plane.

Because each pixel requires multiple iterations, computing large grids becomes computationally expensive. This makes the Mandelbrot set a useful benchmark for comparing different numerical computing strategies in Python.

**Configuration used in the experiments**

| Parameter | Value |
|----------|------|
| Domain | x ∈ [-2.0, 1.0], y ∈ [-1.5, 1.5] |
| Max iterations | 200 |
| Grid sizes tested | several increasing grid sizes |

### 2.1 Numpy Baseline Implementation

The baseline implementation was written with NumPy arrays, generating the coordinates using np.linespace and then combined into a grid covering the selected area. At each iterarion Mandelbrot was applied to all active points using NumPy operations and avoided unnecesary updates thanks to the escape policy.
```python
def mandelbrot_single(width, height, max_iter,
                      xmin=XMIN, xmax=XMAX, ymin=YMIN, ymax=YMAX):
    _, out = mandelbrot_rows(
        0, height, width, height, max_iter,
        xmin=xmin, xmax=xmax, ymin=ymin, ymax=ymax
    )
    return out
```

The advange of this version is that is simple and avoid Python overheads thanks to the NumPy operations. However it runs on a single machine without multiprocessing.


### 2.2 Multiprocessing Implementation
The multiprocessing implementation parallelizes the Mandelbrot computation by dividing the image into chunks of rows. Each task corresponds to a block of consecutive rows, and each worker process computes one block independently using the same NumPy-based Mandelbrot kernel.
The assignment specifically requires analyzing the optimal chunk size for different numbers of processes 
P, and comparing execution time and speed-up for different values of P.
```python
def mandelbrot_multiprocessing(width, height, max_iter, processes=4, chunk_rows=64,
                               xmin=XMIN, xmax=XMAX, ymin=YMIN, ymax=YMAX,
                               force_fork=True):
    """
    Divides the image into horizontal chunks and computes each chunk in parallel using multiprocessing.
    """
    tasks = []
    for y0 in range(0, height, chunk_rows):
        y1 = min(y0 + chunk_rows, height)
        tasks.append((y0, y1, width, height, max_iter, xmin, xmax, ymin, ymax))

    if force_fork:
        try:
            ctx = mp.get_context("fork")
        except ValueError:
            ctx = mp.get_context()
    else:
        ctx = mp.get_context()

    out = np.empty((height, width), dtype=np.int32)

    with ctx.Pool(processes=processes) as pool:
        results = pool.starmap(mandelbrot_rows, tasks, chunksize=1)

    for y0, block in results:
        out[y0:y0 + block.shape[0], :] = block

    return out


def time_function(func, *args, repeats=3, **kwargs):
    """
    Returns the best time (minimum) taken by func(*args, **kwargs) over the specified number of repeats.
    """
    times = []
    result = None

    for _ in range(repeats):
        t0 = time.perf_counter()
        result = func(*args, **kwargs)
        t1 = time.perf_counter()
        times.append(t1 - t0)

    return min(times), result

```
This approach makes possible to study how the Mandelbrot kernel behaves with a distributed workload accross multiple processes on the same machine.

### 2.3 Dask Local Implementation
This Dask version uses Dask Array to split the complex grid into blocks and applied the Mandelbrot computation blockwise.
Each block is processed by a local Dask worker and different chunk sizes and amount of workers were tested to study the impact on performance.
```python 
def mandelbrot_block(c_block, max_iter):
    z = np.zeros_like(c_block, dtype=np.complex128)
    counts = np.zeros(c_block.shape, dtype=np.int32)
    active = np.ones(c_block.shape, dtype=bool)

    for i in range(max_iter):
        z[active] = z[active] * z[active] + c_block[active]

        escaped = np.abs(z) > 2.0
        newly_escaped = escaped & active

        counts[newly_escaped] = i + 1
        active &= ~escaped

        if not active.any():
            break

    counts[active] = max_iter
    return counts






    def mandelbrot_dask(width, height, max_iter,
                    chunk_rows=256, chunk_cols=256,
                    xmin=XMIN, xmax=XMAX, ymin=YMIN, ymax=YMAX):
    """
    Returns a lazy Dask array, without computing.
    """

    x = da.linspace(xmin, xmax, width, chunks=chunk_cols)
    y = da.linspace(ymin, ymax, height, chunks=chunk_rows)

    X, Y = da.meshgrid(x, y)
    c = X + 1j * Y

    out = c.map_blocks(
        mandelbrot_block,
        max_iter=max_iter,
        dtype=np.int32
    )

    return out
```

### 4. Benchmarking methodology 

To compare the implementations, a benchmarking procedure was performed.

The Mandelbrot domain and max_iter were kept constant across all experiments, while the grid size 
N×N was increased progressively to study scaling. Timing was measured using time.perf_counter(), and each configuration was repeated 200 times. For each set of repetitions, the best execution time was retained as the representative value.

Key aspects of the methodology:

- For the multiprocessing version, several process counts 
P were tested, together with several values of chunk_rows, in order to identify the optimal chunk size for each process count.
- For the Dask local version, several chunk sizes and several numbers of local workers were tested.
- For the Dask cluster version, the benchmark was executed with the distributed scheduler and the remote workers connected, and several chunk sizes were evaluated.
- For the global comparison, all results were finally compared against the NumPy baseline.

The recorded timing data was exported to different CSV files.

### 5. Experimental Results
### 5.1 Multiprocessing Results
The multiprocessing experiments showed that execution time depend both on then number of processes and the chosen chunk size.
Very small chunks tend to increase overhead because too many tasks are created, while very large chunks reduce the flexibility of the scheduler and may lead to load imbalance between processes.
The corresponding speed-up values show how much faster the multiprocessing version becomes relative to the chosen baseline.

### 5.2 Dask Local Results
This implementation also showed a clear dependency on the chunk size, it must be large enough to keep each task meaningful, but small enough to mantain parallelism.

Using too small chunks led to a higher number of scheduled tasks and therefore larger overhead. More balanced chunk sizes gave better results.

### 5.3 Dask Cluster Results
This version used 1 scheduler and 2 workers, and the results show that distribution also depends strongly on chunk size, in this type of environments, communication and coordination overhead becomes more visible so chunks that are too small become ineffincient and larger chunks may reduce communication frequency and improve throughput.

### 6. Interpretation
The results show that performance is determined not only by the computational kernel itself, but also by the overhead introduced by the execution strategy.
### Multiprocessing Numpy Implementation
Increasing the number of processes reduces execution time but only up to a certain point, the speed-up is not linear because creating tasks, distributing work and reconstructing the image add extra cost. Chunks that are too small produce overhead while too large chunks reduce load balancing quality.
### Dask Local Implementation
Same trade-off, different form. Dask makes easier the parallel execution but it adds an scheduler overhead. The advantages become more visible when the problem is large enough to amortize the task management cost.
### Dask Cluster Implementation
The trade-offs become more pronounced. Distributing the work accross multiple machines increase total available resources but introduces communication, serialization and coordination overhead. This means that this version is only better for larger problem sizes if the chunks are chosen appropriately.

Overall, the experiments confirm that chunk size is a critical pparameter for all the implementations.


### 7. Conclusion
This project compared four methods for computing the Mandelbrot set in Python.
The results show that parallel and distrubuted execution improve performance but when the workload is large enough and the parameters are chosen carefully, being chink size one of the most important factors affecting runtime.
Both multiprocessing and Dask benefited from balanced chunks, while very small or large task sizes generally reduced the performance.
